# مبانی امنیت

## مرز اعتماد

محتوای WebView و تمام داده‌های دریافتی از کلاینت غیرقابل اعتماد هستند؛ حتی اگر از محیط ایتا آمده باشند. تنها اعتبارسنجی سمت Gateway می‌تواند هویت Eitaa را تأیید کند.

## الزامات

- SDK فقط از آدرس رسمی `https://developer.eitaa.com/eitaa-web-app.js` بارگذاری شود.
- `initData` خام به سرور فرستاده و همان‌جا hash آن با HMAC-SHA256 طبق مستند Eitaa بررسی شود.
- `initDataUnsafe` فقط برای متن نمایشی/UX است؛ هرگز برای authorization، انتخاب tenant یا تعیین role استفاده نشود.
- `auth_date` با پنجره زمانی کوتاه و قابل تنظیم کنترل شود؛ replay mitigation سمت سرور اعمال شود.
- Eitaa Bot Token، Service JWT، signing key و secret هرگز وارد bundle، `.env* ` عمومی، log یا repository نشوند.
- توکن‌های نشست در storage پایدار مرورگر ذخیره نشوند؛ طراحی cookie/token نهایی باید با قابلیت‌های WebView و Gateway ارزیابی شود.
- از ارسال داده شخصی/سازمانی غیرضروری به Eitaa خودداری شود.
- خطاها و telemetry نباید initData، token، شماره تلفن یا محتوای تیکت را ثبت کنند.
- CSP، محدودسازی origin، CORS و rate limiting در زمان استقرار اعمال شوند.
- مجوزها در Backend بررسی شوند؛ مخفی کردن دکمه در UI کنترل دسترسی نیست.

## موارد نیازمند تصمیم امنیتی

- روش نگاشت Eitaa user id به employee identity.
- عمر نشست و refresh/revocation.
- مدیریت چند دستگاه و logout.
- سیاست داده‌های قابل نمایش در برنامک.
- نیاز به MFA یا تأیید هویت سازمانی تکمیلی.
- سیاست retention و audit برای درخواست‌ها.

## نکته مهم

اعتبارسنجی hash به‌تنهایی اثبات نمی‌کند که کاربر ایتا همان کارمند سازمانی است. اتصال هویت ایتا به حساب سازمانی باید با یک فرایند قابل اعتماد و مصوب انجام شود.
